# Clobus OData и Synect: технический аудит (25.11.2026)

Цель: понять, что можно получить из облачной 1С на clobus.uz через стандартный интерфейс OData, что из этого уже
умеет Synect и что нужно доделать, чтобы AI-ассистент отвечал на складские и торговые вопросы.

Как помечены утверждения:

- **[Clobus]**: подтверждено статьёй Clobus «Стандартный интерфейс OData» (https://clobus.uz/articles/data_odata, от 14.05.2026).
- **[1С]**: общая возможность платформы 1С (документация ИТС, ссылки из той же статьи), в Clobus отдельно не проверялась.
- **[Код]**: проверено по исходникам Synect.
- **[Проверить]**: неизвестно, нужно проверить на настоящей базе командой `probe-odata`.
- Имена объектов 1С, кроме уже записанных в профиле `clobus-bp-uz` и примеров из статьи Clobus, взяты из **типовых
  конфигураций для РФ**. Это гипотезы: в узбекских конфигурациях имена могут быть другими. Они помечены **(гипотеза)**.

## A. Возможности Clobus OData

### A.1 Подключение

- Все прикладные базы на clobus.uz опубликованы с поддержкой OData. [Clobus]
- Клиент включает доступ в обработке «Настройка автоматического REST-сервиса». В зависимости от конфигурации путь
  такой: «Администрирование», «Администрирование и НСИ» или «Настройки», затем «Синхронизация данных» →
  «Настройки стандартного интерфейса OData». Нужна роль «Полные права»; во Фреше она у владельца абонента. [Clobus]
- На вкладке «Авторизация» создаётся служебный пользователь. Ему назначается роль `УдаленныйДоступOData`, в списках
  пользователей его не видно. На вкладке «Состав» отмечаются публикуемые объекты; подчинённые объекты обработка
  предлагает включить сама. Планы обмена включать не рекомендуется. [Clobus]
- Адрес: `<адрес приложения без кода языка>/odata/standard.odata/<ресурс>?<параметры>`, например
  `https://clobus.uz/a/sbm/12345/odata/standard.odata/Catalog_Номенклатура?$format=json&$filter=Артикул eq '345'`. [Clobus]
- Аутентификация: HTTP Basic. [Clobus]
- Протокол: OData v3 с расширениями и ограничениями 1С. По умолчанию ответ в XML (Atom). JSON включается параметром
  `$format=json` или заголовком `Accept: application/json`. [Clobus]

### A.3 Параметры запроса

| Возможность | Поддержка | Комментарий |
|---|---|---|
| `$metadata` | да [1С] | Synect его читает и разбирает (`ODataHttpClient.GetMetadataAsync`, отчёт `probe-odata`) [Код] |
| Список ресурсов (служебный документ) | да [1С] | `ListResourcesAsync`; форма `{"value":[{"name","url"}]}` [Проверить] |
| `$filter` | да [Clobus] | `eq ne gt ge lt le and or not`, арифметика, строковые функции (`substringof`, `startswith`, `like`…), функции дат (`year`, `month`, `dateadd`, `datedifference`…), `any`/`all` по табличным частям, `cast`, `isof`. Сравнение с `ХранилищеЗначения` не поддерживается |
| `$select` | да [Clobus] | |
| `$orderby` | да [Clobus] | в том числе по реквизиту ссылки (`Контрагент/ИНН`) |
| `$top`, `$skip` | да [Clobus] | постраничная загрузка строится на них |
| `$inlinecount=allpages` | да [Clobus] | количество приходит в `odata.count` |
| `/$count` | да [Clobus] | вместе с `$filter` — [Проверить] |
| `$expand` | да, **только для ссылок** [Clobus] | для табличных частей не нужен и не работает: они уже внутри документа |
| Фильтр по датам | да [Clobus] | `Date ge datetime'2026-10-01T00:00:00'` |
| `allowedOnly=true` | да [Clobus] | без него при ограничениях доступа на уровне записей ответ — 401 |
| Заголовок `1C_OData-DataLoadMode: true` | **не поддерживается в Clobus** [Clobus] | касается только записи, Synect его не шлёт |
| Запись (POST, PATCH/PUT, DELETE, `Post()`, `Unpost()`) | да [Clobus] | Synect запрещает всё, кроме GET (см. B) |

### A.4 Большие объёмы и инкрементальная загрузка

- В статье Clobus **нет** ни ограничений частоты запросов, ни максимального размера страницы, ни механизма отслеживания
  изменений. `DataVersion` упоминается только как поле в примере ответа. [Clobus]
- Платформа 1С не даёт в OData журнала изменений и фильтра «изменено после». У справочников и документов есть
  `DataVersion` (непрозрачная строка: меняется при каждой записи, но сравнивать её на «больше» нельзя). [1С]
- Поэтому в Synect выбран такой способ (уже реализован) [Код]:
  - **полная выгрузка**: постранично читаются только `Ref_Key` и `DataVersion`, затем по ключу дочитываются новые и
    изменившиеся записи; отсутствующие в источнике помечаются удалёнными, только если перечень ключей заведомо полон;
  - **дельта**: справочники сравниваются так же, документы — только в окне дат (`OData:DeltaWindowDays`, 45 дней).
- У регистров `DataVersion` нет. Остатки и обороты берутся срезом (`Balance`) на момент загрузки и заменяют предыдущий
  срез целиком. [1С]

### A.5 Конфигурации Clobus

На clobus.uz есть три прикладных решения: «1С:Бухгалтерия для Узбекистана», «1С:Управление компанией для Узбекистана
3.0» и «1С:Розница для Узбекистана 3.0» [Clobus, главная страница]. **Состав объектов у них разный**, и это главное
ограничение «универсальности»:

- **Бухгалтерия**: склад и взаиморасчёты ведутся в бухгалтерском регистре `AccountingRegister_Хозрасчетный` (счета и
  субконто), отдельных регистров накопления по складу и продажам в типовой БП нет (гипотеза для узбекской версии).
- **Управление компанией** и **Розница**: управленческие регистры накопления (запасы, продажи, расчёты, деньги).
- Стартовый профиль Synect `clobus-bp-uz` написан под Бухгалтерию и не содержит регистров.

## B. Ограничения

1. **Служебный пользователь может писать и физически удалять данные.** Роль `УдаленныйДоступOData` разрешает
   POST/PATCH/DELETE и проведение. В Synect это закрыто дважды: `ODataHttpClient.SendAsync` и `GetOnlyHandler` пропускают
   только GET, есть тест. [Код] Клиенту стоит открыть во вкладке «Состав» только нужные объекты.
2. **Состав опубликованных объектов выбирает клиент.** Если объект не отмечен, ресурса нет в `$metadata`, запрос к нему
   возвращает ошибку. Без участия владельца абонента ничего не получить. [Clobus]
3. **Ограничения доступа на уровне записей**: без `allowedOnly=true` ответ 401. Synect сейчас считает это ошибкой
   доступа и переводит подключение в NeedsAttention. [Код] Как на это отвечает Clobus — [Проверить].
4. **Лимиты Clobus на частоту запросов и размер ответа не опубликованы.** В Synect свои ограничения: 5 запросов в
   секунду, страница 500, таймаут 60 с, повторы при 429/5xx. [Код] Реальные пределы — [Проверить].
5. **Нет отслеживания изменений.** Каждая полная выгрузка перечитывает все ключи сущности (см. A.4).
6. **Себестоимость.** В Бухгалтерии она есть только в проводках (`Хозрасчетный`, кредит счетов запасов), в Рознице и
   Управлении компанией — в регистрах себестоимости или продаж (гипотеза). Простого поля «себестоимость продажи» нет.
7. **Имена объектов и реквизитов узбекских конфигураций неизвестны.** Весь профиль `clobus-bp-uz` помечен
   `"verify": true`; перечень непроверенного — в `docs/clobus-odata.md`, раздел «Что НЕ проверено».
8. **Виртуальные таблицы регистров сложнее обычных ресурсов**: параметры передаются в скобках
   (`Balance(Period=datetime'…', Condition='…')`), субконто приходят полями `ExtDimension1`…`ExtDimension3` с
   составным типом (`_Type`). Synect такие запросы сейчас строить не умеет (см. D). [Код]
9. **Планы обмена** публиковать не рекомендуется. [Clobus]
10. **Параллельные запросы** в статье не описаны. Synect грузит сущности последовательно и ограничивает частоту
    [Код]. Насколько Clobus терпит параллельность, — [Проверить]; делать её по умолчанию не стоит.

## D. Аудит Synect

### D.1 Ответы на вопросы постановки

1. **Есть ли универсальный механизм подключения к внешним API?** Да. `connections` (вид адаптера, настройки),
   `connection_secrets` (пароли шифруются ASP.NET Data Protection, `DataProtectionSecretStore`), `AdapterRegistry`,
   общие повторы и ограничение частоты (`Application/Resilience`), очередь заданий `sync_jobs` и журнал `sync_runs`,
   планировщик в `Synect.Worker`, правила внимания по подключениям. На этом уже работают Kapital Bank, Didox и OData. [Код]
2. **Можно ли использовать её для OData?** Уже используется: вид подключения `onec_fresh_odata`,
   `ODataConnectionService`, `ODataHttpClient`, `ODataSyncService`, профиль соответствия в JSON. [Код]
3. **Есть ли импорт справочников и документов?** Да. Единый приёмник 1С `IngestService`
   (`POST /ingest/1c/v1/batches` для расширения 1С и прямой вызов для OData) со схемой `IngestSchema`: полные и
   дельта-выгрузки, хэши, пометка удалённых, защита от массового удаления, свежесть по группам данных. [Код]
4. **Где хранить данные?** В существующих таблицах приёмника, ничего параллельного не нужно:

   | Сущность приёмника | Таблица | Наполняется OData сейчас |
   |---|---|---|
   | `counterparties` | `accounting_counterparties` | да |
   | `contracts` | `accounting_contracts` | да |
   | `bank_accounts` | `accounting_bank_accounts` | да |
   | `documents` (+ `lines`) | `accounting_documents`, `accounting_document_lines` | да (реализация, поступление) |
   | `bank_documents` (+ `settlements`) | `accounting_bank_documents`, `accounting_bank_document_settlements` | да |
   | `payment_orders` | `accounting_payment_orders` | нет |
   | `settlement_balances` | `accounting_settlement_balances` | **нет** |
   | `bank_account_balances` | `accounting_bank_account_balances` | нет |
   | `items`, `categories` | `catalog_items`, `catalog_categories` | **нет** |
   | `price_types`, `prices` | `catalog_price_types`, `catalog_prices` | **нет** |
   | `warehouses`, `stock` | `catalog_warehouses`, `catalog_stock` (текущий срез) | **нет** |
5. **Как AI получает данные?** Через MCP-сервер `Synect.Mcp`. Инструменты только читают, работают в транзакции
   арендатора с RLS, с параметризованным SQL, таймаутом и пагинацией, и в каждом ответе отдают свежесть данных. По 1С
   есть `get_1c_documents`, `get_1c_payment_orders`, `get_1c_settlement_balances`, `get_1c_bank_account_balances`,
   `compare_bank_with_1c`, `compare_didox_with_1c` и другие. **Инструментов по каталогу, остаткам и строкам
   документов нет.** [Код] Для AI неважно, пришли данные из расширения 1С или из OData.
6. **Что уже есть и что придётся сделать?** См. D.2 и D.3.

### D.2 Что уже реализовано в OData-коннекторе

| Требование постановки | Состояние | Где |
|---|---|---|
| 1. Адрес облачной базы | есть; только HTTPS, белый список хостов (`clobus.uz`), без IP, без перенаправлений, защита от внутренних адресов | `ODataEndpoint`, `ODataOptions` |
| 2. Логин и пароль | есть; пароль только из переменной окружения, хранится зашифрованным, не логируется | `ODataConnectionService`, `ODataCredentials`, `connection_secrets` |
| 3. Подключение | есть; Basic, только GET | `ODataHttpClient`, `GetOnlyHandler` |
| 4. `$metadata` | есть | `GetMetadataAsync`, `probe-odata` |
| 5. Определение сущностей | частично: `probe-odata` перечисляет ресурсы, поля и типы и пишет отчёт в `docs/odata-probe-<дата>.md`; в настройки подключения это не сохраняется | `ODataCommands` |
| 6–8. Каталог объектов и выбор для синхронизации | **нет как функции**. Выбор задаётся профилем JSON (файл, папка `OData:ProfilesPath` или `profile_json` в настройках подключения). Интерфейса нет | `ODataProfile` |
| 9. Постраничная загрузка | есть; `$top/$skip`, `$orderby=Ref_Key`, `$inlinecount` | `ODataSyncService` |
| 10. Фильтр по датам | есть; окно дельты по `Date` | `ODataSyncService` |
| 11. Обновление ранее загруженного | есть; по `DataVersion`, пометка удалённых при полной выгрузке | `ODataSyncService`, `IngestService` |
| 12. Последняя успешная синхронизация | есть; по каждой сущности (`ingest_batches`, `full_attempt`), `get_connections_overview`, правило `connection.full_sync_overdue` | `ODataFullSyncState` |
| 13. Ошибки соединения и авторизации | есть; повторы при таймауте, сетевых ошибках, 429, 5xx; 401/403 — NeedsAttention | `ODataHttpClient` |

### D.3 Чего не хватает

1. **Регистров.** Модель профиля рассчитана на объекты с `Ref_Key` и `DataVersion`; проверка имён в `ODataUrl`
   (`^[\p{L}\p{N}_]+$`) не пропустит `.../Balance(Period=…)`. Нужен второй вид источника в профиле: **срез** (snapshot)
   виртуальной таблицы без ключа и версии, который целиком заменяет предыдущий срез (у `catalog_stock` и
   `accounting_settlement_balances` в приёмнике уже есть такая семантика: полная выгрузка удаляет пропавшие строки).
2. **Сущностей каталога в профиле**: номенклатура, группы, склады, виды цен, цены, остатки. Таблицы и приёмник есть.
3. **Профилей под «Управление компанией» и «Розницу»**: другие документы и регистры (см. C).
4. **Документов движения товара**: перемещение, списание, возвраты, розничные продажи. В `accounting_documents` есть
   `doc_kind`/`doc_type`, но приёмник понимает только `Sales`/`Purchase`; для движений нужно решение (новые виды
   документов или отдельная таблица движений).
5. **MCP-инструментов по товарам**: остатки, продажи по номенклатуре, оборот товара, сравнение периодов по 1С.
6. **Каталога доступных объектов как данных**: сохранение результата разбора `$metadata` в настройки подключения и
   сравнение его с профилем («в профиле есть, в базе не опубликовано»). Это даёт понятную ошибку вместо 404.
7. **Проверки на настоящей базе**: ни одно имя профиля ещё не сверено с Clobus.

## E. Архитектура интеграции

```
 Clobus (1С:Фреш)                        Synect
 ─────────────────                       ──────────────────────────────────────────────────────────────
 /odata/standard.odata                   Synect.Worker: планировщик → sync_jobs
   Catalog_*        ──GET, Basic──►      ODataSyncService (режим Auto по сущности)
   Document_*  (ТЧ внутри)                 ├─ ODataHttpClient: только GET, 5 rps, повторы, белый список хостов
   AccountingRegister_*/Balance  ┐         ├─ профиль JSON: ресурс → поля приёмника (+ подстановки по ссылкам)
   AccumulationRegister_*/Balance├─(новое) ├─ срезы регистров (новое): снимок целиком
   InformationRegister_*/SliceLast┘        └─ ODataRecordMapper → пакеты приёма
                                         IngestService (тот же приёмник, что у расширения 1С)
                                           └─ accounting_* / catalog_* / ingest_batches / ingest_freshness
                                         Analytics / Accounting1C / Attention (правила, свежесть)
                                         Synect.Mcp: инструменты только для чтения, RLS, свежесть в ответе
                                           └─ AI-ассистент
```

Принципы, которые уже соблюдены и которые надо сохранить:

- один приёмник для расширения 1С и OData; аналитика и MCP не знают об источнике;
- соответствие полей — данные (JSON-профиль), а не код; новые конфигурации добавляются профилем;
- у организации одно активное подключение 1С;
- AI получает агрегаты, посчитанные кодом, а не сырые выгрузки (правило из аудита 19.11: без LLM-арифметики).

S — до 2 дней, M — до недели, L — больше недели. Оценки без учёта ожидания тестовых баз.

## G. Риски

| Риск | Что может случиться | Что уже сделано / что сделать |
|---|---|---|
| **Безопасность: запись через OData** | утечка пароля даёт возможность менять и физически удалять данные клиента | только GET в двух местах, пароль зашифрован и не логируется; клиенту — открыть минимум объектов, менять пароль при подозрении |
| **Безопасность: адрес** | подмена адреса на внутренний сервис (SSRF) | HTTPS, белый список хостов, запрет IP и перенаправлений, проверка разрешённых адресов |
| **Имена в узбекских конфигурациях** | профиль не совпадает с базой, загрузка пустая или с ошибкой | этап 0 и каталог объектов (этап 1) |
| **Различия трёх конфигураций** | «универсальный» профиль не работает на УК и Рознице | профиль на каждую конфигурацию; авто-выбор по `$metadata` |
| **Производительность Clobus** | лимиты не опубликованы; полная выгрузка перечитывает все ключи; запросы `Balance` по большим регистрам тяжёлые | 5 rps, страница 500, полная раз в сутки, документы в дельте по окну; срезы регистров — с узким `Condition` по счетам, ночью; замерить на настоящей базе |
| **Большие объёмы** | долгая первая выгрузка, длинные URL у фильтра из 20 ключей | `probe-odata` меряет время; при необходимости уменьшить пакет ключей |
| **Неполный перечень ключей** | ложная пометка удалённых | уже: пометка только при полном перечне, защита от массового удаления, ручное подтверждение |
| **Актуальность** | AI отвечает по вчерашним остаткам | свежесть в каждом ответе MCP, `connection.stale_data`, дневные обновления каждые 2 ч; остатки — это срез на время загрузки, в ответе указывать `as_of` |
| **Ограничения доступа на записи** | 401 без `allowedOnly=true` при RLS в 1С | выяснить на настоящей базе; при необходимости добавлять `allowedOnly=true` и предупреждать о неполноте |
| **Методика наценки и себестоимости** | AI выдаёт «наценку» по разным правилам в разных базах | считать в коде, возвращать методику вместе с цифрой |

## H. Сценарии AI-ассистента

Колонка «Только OData?»: можно ли получить ответ одним запросом OData без обработки на стороне Synect.

| Вопрос | Объекты 1С | Поля | Связи | Только OData? | Что есть в Synect |
|---|---|---|---|---|---|
| Сколько товаров на складах? | БП: `Хозрасчетный/Balance` по счетам запасов; УК/Розница: регистр запасов `/Balance` | номенклатура, склад, количество, сумма | номенклатура, склады | Да, если опубликован регистр; итог по количеству разных единиц складывать нельзя, нужна группировка в коде | `catalog_stock` есть, не наполняется; инструмента нет |
| Остатки по складу | то же с отбором по складу | то же | склады | Да | то же |
| Какие товары заканчиваются? | остатки + продажи из строк реализации | количество, продажи за период | номенклатура | **Нет**: нужен порог или средний расход, считается в Synect | нет порогов и инструмента |
| Сколько продано за месяц? | `Document_РеализацияТоваровУслуг` (+ возвраты, розничные продажи) или регистр продаж `/Turnovers` | дата, сумма, строки | контрагент, номенклатура | Частично: суммы по документам — да; чистые продажи с возвратами — обработка | документы и строки грузятся; `get_1c_documents` выдаёт список, но не итог |
| Лучшие товары | строки реализации или регистр продаж | номенклатура, количество, сумма | номенклатура | Нет (группировка строк в Synect); с регистром продаж — частично | строки есть, инструмента нет |
| Сумма закупок за месяц | `Document_ПоступлениеТоваровУслуг` (+ возвраты поставщику) | дата, сумма | контрагент | Частично | документы грузятся, итога нет |
| Сколько нам должны? | БП: `Хозрасчетный/Balance` по счетам расчётов; УК: `РасчетыСПокупателями/Balance` | контрагент, договор, сумма | контрагенты, договоры | Да, если опубликован регистр | `get_1c_settlement_balances` есть, таблица OData не наполняется |
| Просроченная дебиторка | остатки расчётов по документам + срок оплаты из договора | документ, дата, сумма, `СрокОплаты` | документ, договор | **Нет**: срок и старение считаются в Synect; в БП остаток по документам есть, только если ведётся учёт по документам расчётов | `payment_term_days` грузится; инструмента старения по 1С нет |
| Динамика продаж | реализации | дата, сумма | — | Нет (группировка по месяцам в Synect) | нет |
| Наибольшая наценка | строки реализации и поступления, `ЦеныНоменклатуры`, себестоимость из регистров | цена, количество, себестоимость | номенклатура | **Нет**: методика и расчёт в Synect, в БП точной себестоимости по товару нет | нет |
| Движение товара | реализации, поступления, перемещения, списания, возвраты или движения регистра запасов (`_RecordType`) | дата, документ, склад, количество | номенклатура, склады | Частично: движения регистра — да (УК/Розница) | грузятся только реализации и поступления |
| Сравнить два периода | реализации | дата, сумма, строки | контрагент, номенклатура | Нет (две выборки и разница в коде, не в модели) | сравнение есть только по банку (`compare_counterparty_periods`) |
