# 1C:Fresh (Clobus) через OData

Коннектор `onec_fresh_odata` читает облачное приложение 1С:Фреш на clobus.uz по стандартному интерфейсу OData и
кладёт данные в те же таблицы `accounting_*` через тот же приёмник (`IngestService`), что и расширение 1С. Сверка,
аналитика и инструменты MCP не меняются: для них это обычные данные 1С.

Источник: статья Clobus «Стандартный интерфейс OData» (clobus.uz/articles/data_odata). На настоящем приложении
коннектор **ещё не проверялся** — см. раздел «Что не проверено».

## Как клиент включает OData

Все приложения на clobus.uz уже опубликованы с поддержкой OData; клиенту нужно создать служебного пользователя и выбрать,
какие объекты открыть. Нужны права «Полные права» (во Фреше — владелец абонента).

1. Открыть обработку «Настройка автоматического REST-сервиса» одним из путей (зависит от конфигурации):
   - **Администрирование → Синхронизация данных → Настройки стандартного интерфейса OData**;
   - Администрирование и НСИ → Синхронизация данных → Настройки стандартного интерфейса OData;
   - Настройки → Синхронизация данных → Настройки стандартного интерфейса OData.
2. Вкладка **«Авторизация»**: создать отдельного служебного пользователя (логин и пароль). Ему автоматически назначается
   роль `УдаленныйДоступOData`; в списках пользователей приложения и менеджера сервиса он не виден.
3. Вкладка **«Состав»**: отметить только нужные объекты (список ниже). Если нужен подчинённый объект, обработка
   предложит включить его сама. Планы обмена не включать. «Записать и закрыть».
4. Передать нам: адрес приложения из строки браузера без кода языка (например `https://clobus.uz/a/<конфигурация>/<номер>`),
   логин и пароль служебного пользователя — по защищённому каналу, не в почте и не в чате.

### Какие объекты включать (стартовый профиль `clobus-bp-uz`)

| Что | Объект 1С | Ресурс OData |
|---|---|---|
| Контрагенты | Справочник «Контрагенты» | `Catalog_Контрагенты` |
| Договоры | Справочник «Договоры контрагентов» | `Catalog_ДоговорыКонтрагентов` |
| Банковские счета организации | Справочник «Банковские счета» | `Catalog_БанковскиеСчета` |
| Реализация | Документ «Реализация товаров и услуг» (с табличными частями «Товары», «Услуги») | `Document_РеализацияТоваровУслуг` |
| Поступление | Документ «Поступление товаров и услуг» («Товары», «Услуги») | `Document_ПоступлениеТоваровУслуг` |
| Поступление на счёт | Документ «Поступление на расчётный счёт» («Расшифровка платежа») | `Document_ПоступлениеНаРасчетныйСчет` |
| Списание со счёта | Документ «Списание с расчётного счёта» («Расшифровка платежа») | `Document_СписаниеСРасчетногоСчета` |
| Справочники для подстановки | «Валюты», «Банки», «Номенклатура», «Статьи движения денежных средств», план счетов «Хозрасчетный» | `Catalog_Валюты`, `Catalog_Банки`, `Catalog_Номенклатура`, `Catalog_СтатьиДвиженияДенежныхСредств`, `ChartOfAccounts_Хозрасчетный` |

Имена — из учебной «Бухгалтерии предприятия» 3.0 (docs/mapping.md расширения); в узбекской конфигурации они могут
отличаться. `probe-odata` показывает, что опубликовано на самом деле.

## Риск: служебный пользователь может писать и удалять

Роль `УдаленныйДоступOData` даёт не только чтение: по тому же интерфейсу можно создавать (POST), изменять (PATCH/PUT),
проводить и **физически удалять** (DELETE, без пометки удаления) объекты. Поэтому:

- клиент Synect отправляет **только GET**: любой другой метод бросает исключение до отправки (`ODataHttpClient.SendAsync`)
  и ещё раз отсекается в цепочке обработчиков (`GetOnlyHandler`); это покрыто тестом;
- пароль хранится только в зашифрованном хранилище секретов подключения (`connection_secrets`), не попадает в логи,
  сообщения об ошибках, настройки подключения и коммиты; заголовок `Authorization` и адрес с паролем не логируются;
- клиенту стоит открыть во вкладке «Состав» только перечисленные объекты и при утечке сменить пароль служебного
  пользователя (после смены — `set-credentials`/пересоздание подключения на нашей стороне).

## Как подключить у нас

```
# пароль только через переменную окружения, никогда аргументом
$env:SYNECT_ODATA_PASSWORD = "..."
dotnet run --project src/Synect.DevTools -- probe-odata --url https://clobus.uz/a/<конфигурация>/<номер> --user <логин>
dotnet run --project src/Synect.DevTools -- create-connection --tenant <организация> --kind onec_fresh_odata --url https://clobus.uz/a/<конфигурация>/<номер> --user <логин> [--profile clobus-bp-uz] [--organization-key <guid>] --test
dotnet run --project src/Synect.DevTools -- sync-odata --tenant <организация> --connection "1C:Fresh (OData)" --mode full --dry-run
Remove-Item Env:SYNECT_ODATA_PASSWORD
```

- `probe-odata` пишет отчёт в `docs/odata-probe-<дата>.md`: `$metadata`, список ресурсов, `/$count`, поля первой записи с
  типами (без значений), фильтр по `Date` и по `DataVersion`, две страницы `$top/$skip`, время ответов. Хоста, номера
  приложения, значений и ИНН в отчёте нет.
- `--organization-key` — `Ref_Key` организации, если в базе их несколько (иначе договоры, счета и документы всех
  организаций базы попадут в одну организацию Synect).
- У организации может быть **только одно активное подключение 1С** (`onec_extension` или `onec_fresh_odata`). Чтобы
  сменить источник: `disable-connection --tenant <организация> --connection <старое>`, затем создать новое. Didox,
  банки и импорт выписок правилом не затрагиваются.

## Как работает загрузка

- Адрес (`base_url`): только HTTPS, хост из `OData:AllowedHosts` (по умолчанию `clobus.uz` и его поддомены), без логина и
  пароля в адресе, без IP-адресов, без перенаправлений; при соединении отклоняются внутренние адреса (loopback, частные,
  link-local), в которые разрешается имя хоста. `http://localhost` — только в Development и только с
  `OData:AllowHttpLocalhostInDevelopment = true`.
- Планировщик ставит задания только pull-подключениям: ночью и днём каждые `OData:DaytimeRefreshHours` (2).
- **Режим Auto решает по каждой сущности отдельно** (контрагенты, договоры, счета, документы, банковские документы), по
  времени её последней **завершённой** полной выгрузки из журнала `ingest_batches` (пакет `mode='full'` с `is_last_batch`
  и все номера пакетов этой выгрузки обработаны):
  - полная нужна, если с последней завершённой прошло не меньше `OData:FullSyncInterval` (24 ч) минус
    `OData:FullSyncTolerance` (2 ч) — так ночной слот, который каждый день начинается в одно и то же время, даёт полную
    выгрузку каждые сутки (без допуска она сползала на слот в день, а при расписании «раз в сутки» шла раз в двое суток);
  - после незавершённой попытки (неполный перечень ключей, удержание защитой, ошибка) следующая полная попытка этой
    сущности — не раньше чем через `OData:FullRetryAfter` (12 ч), между попытками идёт дельта;
  - сущность, у которой полная не завершается, не мешает остальным: они идут по своему графику;
  - DevTools `--mode full` / `--mode delta` задаёт режим всем сущностям явно, без этих правил.
- Каждая попытка полной выгрузки отмечается в `ingest_batches.envelope_extra.synect_odata.full_attempt` первого пакета
  сущности: `outcome` = `full` (ушла как полная), `incomplete_list`, `held_back` (защита от удаления) или `error`, и
  `reason`. Попытка, закончившаяся ошибкой, записывается пустым пакетом-дельтой с причиной (тип ошибки и наше сообщение,
  без значений и хоста). Пакеты OData сами не меняют статус подключения и свежесть: это делается один раз после
  успешной загрузки целиком.
- **Полная**: по каждой сущности постранично ключи и `DataVersion` (`$select=Ref_Key,DataVersion`, `$orderby=Ref_Key`,
  `$top/$skip`, `$inlinecount=allpages`), затем полностью читаются только новые и изменившиеся записи (фильтр
  `Ref_Key eq guid'…' or …`), пакеты уходят в приёмник как полная выгрузка; ключи неизменившихся тоже сообщаются
  приёмнику, поэтому завершённая выгрузка помечает удалёнными ровно отсутствующие в источнике записи (существующий
  механизм полной выгрузки).
- **Полная выгрузка помечает удалённые, только если перечень ключей заведомо полон**: сервер вернул `odata.count` и
  собрано ровно столько ключей; если `odata.count` нет — сверка с `/$count`. Если счётчик менялся между страницами,
  страницы повторились, число не сошлось или `/$count` недоступен, сущность уходит дельтой (без `is_last_batch`, без
  пометки удалённых), запуск помечается незавершённым, причина — в предупреждениях отчёта и в журнале.
- **Защита от массового удаления** (`OData:MassDeleteGuard`: `Enabled` true, `MaxShare` 0.2, `MinCount` 50): если из
  активных записей сущности пропало больше 20% и таких не меньше 50, или источник вернул пустой список при существующих
  активных записях, выгрузка уходит дельтой, запуск незавершён, пункт внимания `connection.incomplete_load` с деталями
  `mass_delete_blocked` (сущность, число, доля); в журнал пишется предупреждение, в `ingest_batches.envelope_extra` —
  отметка `synect_odata.mass_delete_blocked`. Пропустить такую выгрузку можно только вручную:
  `sync-odata --mode full --confirm-mass-delete` (без `--dry-run`); имя оператора (`пользователь@машина`) записывается в
  `envelope_extra.synect_odata.mass_delete_confirmed` пакета выгрузки и в журнал. Планировщик подтверждать не умеет.
- Загрузки из DevTools (не `--dry-run`) записываются как обычные запуски (`sync_runs`), как и загрузки очереди.
- После каждой загрузки OData пересчитываются правила внимания по подключениям: `connection.needs_attention`,
  `connection.stale_data` (как у банка и Didox, `Attention:StaleAfter`) и `connection.incomplete_load`. Для расширения 1С
  `stale_data` и `incomplete_load` по-прежнему не применяются (его свежесть показывает `get_connections_overview`).
- **`connection.full_sync_overdue`** (High, только `onec_fresh_odata`): по сущности не было завершённой полной выгрузки
  дольше `OData:FullSyncOverdueDays` (3 дня; без завершённых — считая от создания подключения). Один пункт на сущность,
  в деталях: `entity`, `last_full_sync_at`, `last_attempt_at`, `last_outcome`, `last_failure`. Дельты его не закрывают,
  закрывает завершённая полная выгрузка этой сущности.
- `get_connections_overview` у подключения OData показывает `full_syncs`: по каждой сущности `last_full_sync_at`,
  `last_attempt_at`, `last_outcome` и `last_failure` (если последняя попытка не завершилась).
- Числа в записи приёма — в одной канонической форме: суммы, количество, суммы строк с НДС и числовая ставка НДС пишутся
  десятичной строкой без хвостовых нулей и экспоненты (`6`, `"6"`, `"6.0000"`, `6.00` → `"6"`), поэтому одно и то же
  значение всегда даёт ту же запись и тот же хэш.
- **Дельта**: справочники сравниваются так же, без пометки удалений; документы — только с датой в окне
  `OData:DeltaWindowDays` (45 дней).
- `DataVersion` хранится в `extra.data_version` записи, признак пометки удаления в самой 1С — в `extra.source_deleted`
  (чтобы отличить его от пометки полной выгрузкой и вернуть запись, если она снова появилась).
- Источник каждой записи: `last_batch_id → ingest_batches.connection_id`; у пакетов OData `ingest_key_id` пуст.
- Запросы: не больше `OData:RequestsPerSecond` (5) в секунду, таймаут `OData:RequestTimeout` (60 с), повторы с растущей
  паузой при таймауте, сетевой ошибке, 429 (с учётом `Retry-After`) и 5xx; 401/403 — сразу ошибка доступа, подключение
  уходит в NeedsAttention.
- Профиль соответствия — JSON (`src/Synect.Application/OData/Profiles/clobus-bp-uz.json`), не код. Его можно заменить без
  пересборки: файл `<имя>.json` в папке `OData:ProfilesPath` или целый профиль в настройках подключения (`profile_json`).

## Что НЕ проверено на настоящем приложении

Всё ниже основано на документации Clobus и учебной БП и помечено в коде `TODO(verify-real)`, в профиле `"verify": true`.

1. Имена ресурсов, реквизитов и табличных частей узбекской конфигурации (весь профиль `clobus-bp-uz`).
2. Значения перечислений: `ЮридическоеФизическоеЛицо`, `ВидДоговора`, `СтавкаНДС` (`НДС12`, `НДС12_112`, `БезНДС`, …) —
   приходят ли они именами значений и какими.
3. Составные ссылки (`Контрагент`, `Сделка`, `Owner`): форма «значение + `<имя>_Type`» со значением
   `StandardODATA.Catalog_…`.
4. Отбор по типу владельца `Owner_Type eq 'StandardODATA.Catalog_Организации'` и по `Организация_Key`.
5. `$orderby=Ref_Key` поддерживается и даёт стабильный порядок между страницами.
6. Табличные части приходят массивами внутри документа без `$select`/`$expand`.
7. Фильтр по ключам `Ref_Key eq guid'…' or …` из 20 условий (длина URL, нагрузка).
8. `$inlinecount=allpages` и `odata.count` строкой на больших выборках; `/$count` — простым числом.
9. Фильтр по `DataVersion` (только в `probe-odata`, загрузка его не использует).
10. Кодирование `'` как `%27` и кириллицы в пути — 1С принимает percent-encoding.
11. Ответ служебного документа (`?$format=json`) — форма `{"value": [{"name", "url"}]}`.
12. Код банка (МФО) в `Catalog_Банки.Code`, счёт учёта в `ChartOfAccounts_Хозрасчетный.Code`, валюта — `Description`
    буквенным кодом или `Code` цифровым.
13. Поведение при больших объёмах: время ответа, лимиты Clobus на частоту запросов (в документации не указаны),
    размер страницы 500.
14. Как 1С отвечает при ограничениях доступа без `allowedOnly=true` (по документации — 401; сейчас это ошибка доступа).
16. Тип реквизита ставки НДС (перечисление или ссылка на справочник «Ставки НДС»): `probe-odata` показывает его в разделе
    «VAT rate attribute»; для ссылки стартовый профиль не подходит (нужна подстановка из справочника).
17. Отдаёт ли Clobus `odata.count` при `$inlinecount=allpages` и работает ли `/$count` с `$filter`: без них полная выгрузка
    никогда не завершится (всегда дельта, удалённые не помечаются).
15. Не перенесены из mapping.md: ЭСФ (`esf_*`), срок оплаты документа (`due_date`, регистр сведений), табличная часть
    «Оборудование» поступления, условие `УстановленСрокОплаты` для `payment_term_days`, `is_active` по дате закрытия счёта.
